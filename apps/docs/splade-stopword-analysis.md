# SPLADE 불용어 오염 분석 — "상세" 사례와 대응 방안

> 대상: 검색 담당자 / 파이프라인 담당자 공유용
> 작성 배경: `전기 자동차 배터리` 검색 시 SPLADE에서 `상세` 같은 무관 토큰이 잡히는 현상, 그리고 두 도메인 질의(`반도체 + 인공지능`)에서 한쪽만 강한 문서가 양쪽을 모두 만족한 문서보다 높게 나오는 문제와 연결됨.
> 근거 데이터: 실제 PIXIE-Splade-v1.0 모델 출력. 재현: `apps/tools/sparse_stopwords.py`(전체 코퍼스 DF/IDF) · `apps/tools/diagnose_retrieval.py`. 계산식은 `apps/search/encoders.py`(`SpladeSparseEncoder.embed`)와 동일. (구 v1.x 경로 `src/embedder.py`는 `legacy_v1x/ingest/embedder.py`로 이동.)

---

## 1. 한 줄 요약

SPLADE는 입력에 없는 단어까지 "관련 있을 법한 어휘"로 **확장(expansion)** 한다. `상세` 같은 도메인 빈출 일반어가 거의 모든 문서·질의에서 ~1.0의 weight로 켜지는데, **SPLADE에는 IDF 억제가 없어** 이 무의미한 토큰이 점수에 그대로 더해진다. 실측상 `상세`가 실제 `배터리` 매칭보다 점수 기여가 더 크다. 현재 로컬 SPLADE encoder는 상위 64개 token만 남기는 top-k pruning을 적용한다.

---

## 2. 왜 생기나 (메커니즘)

SPLADE = **SP**arse **L**exical **A**n**D** **E**xpansion. 운영 코드의 핵심 계산:

```python
# apps/search/encoders.py
token_scores = torch.log1p(torch.relu(logits)) * attention_mask
sparse_batch = torch.max(token_scores, dim=1).values   # 어휘 전체(~5만)에 대한 max-pool
```

- `logits`는 BERT의 **MLM 헤드**가 내놓는 **어휘 전체에 대한 점수**다. 입력에 실제 등장한 토큰만이 아니라, "이 문맥에서 나타날 법한 모든 토큰"에 점수가 매겨진다.
- 그래서 `배터리`로 질의해도 모델이 학습한 연관어(`전지`, 영어 `detail` 등)가 0이 아닌 값으로 **추가로 켜진다**. 이건 버그가 아니라 SPLADE의 설계 목적(어휘 불일치 해결: `배터리`↔`전지` 매칭).

**문제는 무엇이 확장되느냐다.** `상세`가 켜지는 이유:

1. **코퍼스 극빈출 일반어** — 특허 명세서의 「상세한 설명」, 과제·논문의 "상세 내용/상세하게". 모델이 "기술 문서 문맥 → 상세"를 강하게 학습.
2. **IDF로 눌리지 않음** — BM25는 `modifier_idf: true`로 고빈도어가 자동 강등되지만, **SPLADE에는 IDF가 없다**(YAML 주석에도 "bm25 backend에서만"). 90% 문서에 다 켜지는 변별력 0의 토큰도 weight가 살아있다.
3. **pruning만으로는 불충분** — 현재 로컬 SPLADE encoder는 상위 64개 token만 남긴다. 하지만 `상세/detail`은 쿼리에서 핵심어급 순위로 올라오므로 top-k pruning 안에 남는다. top-k는 꼬리 token과 인덱스 크기 제어에는 도움이 되지만, 고가중 편재 token 자체를 해결하지는 못한다.

## 3. 실측 데이터 — "상세" weight 분포

쿼리 + 성격이 다른 문서 텍스트를 실제 모델에 넣어 SPLADE 벡터를 디코딩한 결과.
(짧은 합성 문장 기준. 현재 로컬 encoder top-k pruning은 64.)

| 텍스트 | "상세" 리터럴 포함? | 상세 weight | 순위 | top_k 생존 |
|---|---|---|---|---|
| **쿼리** `전기 자동차 배터리` | ❌ 없음 | **2.063** | **2 / 204** | ✅ |
| **쿼리** `반도체와 인공지능 관련 연구자 추천` | ❌ 없음 | 0.942 | 24 / 155 | ✅ |
| DOC 리튬이온 이차전지 (EV, 관련) | ❌ 없음 | 1.081 | 16 / 112 | ✅ |
| DOC 전고체 배터리 …상세한 설명 | ✅ 있음 | 1.071 | 15 / 142 | ✅ |
| DOC 항공우주 위성 (무관) | ❌ 없음 | 0.958 | 23 / 121 | ✅ |
| DOC 유전체 신약 (무관) | ❌ 없음 | 1.037 | 21 / 109 | ✅ |
| DOC 무선통신 특허 …상세한 설명 | ✅ 있음 | 1.070 | 14 / 125 | ✅ |

### 데이터가 말해주는 것

1. **"상세"는 리터럴이 아니라 확장이다.** 항공/바이오 문서엔 "상세"라는 글자가 **없는데도** weight ~1.0로 켜진다. 영어 `detail`도 같이 켜진다(쿼리1 TOP15에 `detail=1.68`). → **원문 텍스트를 훑어서는 못 잡는다 — 글자가 없으니까.**

2. **주제와 무관하게 거의 상수(~1.0) = 변별력 0의 배경 노이즈.** EV든 항공이든 바이오든 0.94~2.06으로 항상 켜진다. 전형적인 sparse 불용어 오염.

3. **쿼리 `전기 자동차 배터리`에서 "상세"가 2위 — 정작 "전기/자동차"보다 높다.** 점수는 내적 `Σ qₜ·dₜ`. 실제로 관련 있는 EV 문서(리튬이온)와의 차원별 기여를 계산하면:

   ```
   상세 :  2.063 × 1.081 = 2.23   ← 가장 큰 기여
   자동차:  1.739 × 0.796 = 1.38
   배터리:  2.232 × 0.547 = 1.22
   ```
   **아무 의미 없는 "상세"가 "배터리" 매칭보다 점수에 더 크게 기여한다.**

4. **top-k/min_value로는 "상세"를 못 자른다.** "상세"는 값이 ~1.0~2.06으로 **큰 값**이다. top-k 64 안에 남고, 안전한 임계값(0.1~0.3)으론 안 잘린다. 자르려면 1.0+로 올려야 하는데 그러면 진짜 콘텐츠어(`배터리`=0.547, `자동차`=0.796)가 먼저 죽는다. top-k/min_value는 꼬리 노이즈 정리용이지 이 증상의 해법이 아니다.

> 참고: 위는 짧은 합성 문장이다. 실제 480토큰 청크는 콘텐츠 토큰이 많아 **문서쪽** "상세" 상대순위는 더 내려간다. 다만 **쿼리는 원래 짧으므로 쿼리쪽 2위는 현실 그대로**고, 그게 핵심이다.

## 4. 두 도메인 질의 문제와의 연결

`반도체와 인공지능 관련 연구자` 검색에서 (1) 반도체 ×10, (2) 인공지능 ×10 문서가, (3) 반도체 3 + 인공지능 2 문서보다 높게 나오는 문제는 **별개의 원인이지만 같은 뿌리(점수가 합산/OR 성격)**를 공유한다.

- SPLADE/BM25 점수 = `Σ(토큰별 가중치)` → 한쪽 도메인만 강해도 합계가 커진다. "두 도메인을 모두 가져라"는 제약이 점수식에 없다.
- 여기에 `상세` 같은 노이즈 차원까지 합산되어 신호가 더 희석된다.

→ 근본 해결은 **질의를 도메인 단위로 분해 → 도메인별 검색 → 합산(sum)이 아니라 `min`/곱(coverage) 으로 결합 → 연구자 단위 집계도 `min`** 으로 가는 것. (이 문서의 주제인 불용어 오염 제거는 그 전제로서 신호 품질을 올려준다.) 상세 설계는 별도 협의.

## 5. 대응 방안 — 우선순위

핵심 원리: 점수가 내적이므로 **`q_상세 · d_상세`에서 한쪽만 0으로 만들면 그 차원 기여가 통째로 사라진다.** 따라서 재적재 없는 쿼리쪽부터 시작하는 게 가장 싸고 빠르다.

| 단계 | 내용 | 재적재 | 비고 |
|---|---|---|---|
| **0 (권장 시작점)** | **검색 시점에 쿼리 SPLADE 벡터의 불용어 차원을 0으로 마스킹** (`상세/관련/방법/내용…` + `detail` 등 영문 확장) | ❌ 불필요 | 즉시·가역, A/B 테스트 즉시 가능. 모든 점수에서 해당 차원 기여 제거 |
| **1** | 문서쪽까지 확실히 빼기: **SPLADE 출력 벡터의 차원별 DF(문서빈도) 통계**로 고DF 차원을 불용어로 선정 → 마스킹/IDF 재가중 후 재적재 | ✅ 필요 | SPLADE에 빠진 IDF를 손으로 넣는 것. 가장 타깃 정확 |
| **2** | top-k pruning (꼬리 컷) | ✅ 문서쪽 재적재 시 | 현재 encoder는 **top-k 64 적용됨**(`apps/search/encoders.py`; `min_value`는 미구현). 꼬리·인덱스 크기용. **"상세"는 고가중이라 못 자름** — 0·1단계(IDF)가 본해법. |
| **3** | bm25 backend 전환 | ✅ 필요 | `modifier_idf`로 상세 자동 강등 → 증상 직접 해결. 단 **확장(synonym) 효과 상실**(`배터리→전지` 매칭 불가). Qdrant server-side 지원 확인 필요 |

## 6. 검색 담당자 초기 계획에 대한 피드백

> 담당자 제안: (1) 검색 전 문서를 훑어 비정상 출현 토큰(조사·부사) 제외 → (2) 안 되면 `splade_min_value` 켜고 재적재 → (3) 그래도 안 되면 bm25 전환

방향은 맞다. 다만 실측에 비추어 **두 가지 보정**이 필요하다.

- **계획 1 보정:** 조사/부사는 SPLADE 서브워드 + 라벨제거(`sparse_text`)로 이미 약하다. 진짜 오염원은 `상세/관련/방법/연구` 같은 **준-콘텐츠 빈출어**이고, 결정적으로 **"상세"는 원문에 없다(확장)**. → 빈도를 **원문이 아니라 SPLADE 출력 벡터에서** 재야 한다(위 표 1단계).
- **계획 2 보정:** `splade_min_value`로는 "상세"가 **안 잘린다**(값이 큼, 위 §3-4). 보조 수단으로만.
- **계획 3:** 유효하다. 다만 확장 효과 상실이 트레이드오프. 정밀도 vs 재현율 결정 사항.
- **추가 제안:** 가장 싸고 효과 큰 **쿼리쪽 마스킹(0단계)** 을 재적재 전에 먼저 넣고 효과·부작용을 측정할 것.

```bash
PYTHONUTF8=1 PYTHONIOENCODING=utf-8 \
  SPLADE_MODEL_PATH="D:\models\PIXIE-Splade-v1.0" \
  python apps/tools/diagnose_retrieval.py --query "전기 자동차 배터리" --show-sparse-tokens
```

- 스크립트: `apps/tools/diagnose_retrieval.py` 또는 DF 분석용 `apps/tools/sparse_stopwords.py`
- 쿼리 sparse top token은 `diagnose_retrieval.py --show-sparse-tokens`로 확인한다.
- 현재 로컬 encoder는 `apps/search/encoders.py`에서 상위 64개 token만 반환한다.
